# TVC hardware parser: design and status (V-222 .. V-225, 2026-10-28)

The parser turns a TVC slice (docs/TVC_BITSTREAM_V0.md sections 3 to 5) into syntax elements. It is built bottom-up, every unit checked **bit for bit against the reference decoder** (`tools/tvc_ref`, which has a guarded trace hook `TVC_RC_HOOK`: it reports every slice start, every bin with its context index, probability, bit, range and code, and every coefficient block with its levels).

## 1. Units
| Unit | File | Does | Status |
|---|---|---|---|
| range decoder | `tau_tvc_rc.sv` | the arithmetic: context bin (probability in, bit and updated probability out) and bypass bin; `PIPE` 1: 3 clocks per bin, 134 MHz standalone (V-224); `PIPE` 0: 2 clocks, 104 MHz (66.67 MHz domain) | done, verified, fitted alone |
| bin layer | `tau_tvc_bin.sv` | the 407 probabilities in one M10K, the reset sweep at every slice start (407 clocks), the read / decode / write-back sequence | done, verified |
| coefficient block | `tau_tvc_blk.sv` | `last` tree, significance, greater-than-one, Exp-Golomb remainder, sign; 8x8 (classes 0 luma, 1 chroma) and 4x4 (class 2); emits the non-zero levels, highest scan position first | done, verified |
| fast engine | `tau_tvc_eng.sv` | context RAM + range decoder + block decoder with look-ahead: 3 clocks per bin (section 4c) | done, verified, fitted alone |
| macroblock layer | `tau_tvc_mb.sv` | skip / intra flags, QP delta, intra modes, B list selection, motion vector differences, coded-block flags, transform sizes, sub-block flags; keeps the left / above neighbour state (a register and a line buffer); calls the engine's single-bin and block ports; emits the macroblock record and the tagged levels | done, verified (V-228) |
| vector prediction | `tau_tvc_mvp.sv` | the median of the neighbours' vectors (A left, B above, C above-right or D above-left), the unit's own final vectors (skip: prediction, inter: prediction + difference, intra: 0), left register + above line buffer | done, verified (V-229) |

## 2. Context numbers (the position in the reference's `Ctx` struct, uint16 units, 407 in all)
skip 0-2, intra 3-5, bdir 6-7, mpm 8, rem 9-10, cmode 11-13, cbp[3][3] 14-22, dqz 23-24, dqm 25-27, mvz[2][3] 28-33, mvm[2][6] 34-45, **last[3][64] 46-237, sig[3][13][3] 238-354, gt1[3][3][3] 355-381, lrem[3][6] 382-399**, t4[3] 400-402, cbf4[4] 403-406. The block decoder's numbers are checked against the trace's `idx` on every request (a pure renumbering would be invisible to the arithmetic, which is why that check exists); the macroblock layer must use the same map, one shared RAM.

## 3. Verification
`make test-rtl-tvc-rc` (range decoder alone: 6 traces, both `PIPE`, steady and throttled byte supply), `test-rtl-tvc-bin` (bin layer: 8 traces including 3 real 4x4 streams and 600,000 random bins whose contexts adapt like the real ones), `test-rtl-tvc-blk` (block decoder: **6 real streams, 67,000 coefficient blocks including 16,448 4x4 blocks**, levels, final range / code, and every issued context number compared with the reference), each with mutants (`-mutation` targets: rc 14, bin 8, block 6, all killed). Traces are made by `tools/tvc_ref/tvc_rc_trace` from `tools/tvc_ref/vectors/*.tvc` and `tvc_rc_random`.
Two things the tests taught: a mutant that renumbers contexts consistently is *equivalent* for the arithmetic, so the block test now checks the context numbers themselves; and arbitrary-probability random traces only make sense for the range decoder alone (the bin layer's RAM adapts by itself), so they are a separate trace (`rand_rawp`).

## 4. Measured speed (simulation, 100 MHz variant `PIPE` 1)
**7.7 clocks per bin inside coefficient blocks** (v02 7.85, v04 7.78, v14 7.71; `PIPE` 0: 6.7-6.9), i.e. about **13 M bins/s at 100 MHz**, not the 33 M bins/s the range decoder alone allows and far from the codec scope's target of 2 clocks per bin. Where the clocks go: the request / answer handshake between the block decoder and the bin layer (about 2.7 clocks), the RAM read in front of every bin, the range decoder (3), the write-back and one idle clock before the next request. A level 3 stream averages about 6 M bins/s (estimate), so one lane would be about 48 % busy on average, and the worst legal picture (about 4 M bins) would take about 300 ms on one lane. **This was improved in the fast engine (section 4c)**: the planned ways are (a) read the probabilities of both possible next contexts in parallel with the current bin and pick one by its result (the block decoder knows both successors of the tree, significance and magnitude steps), (b) replace the request / answer handshake by direct registered feedback, (c) forward the written-back probability instead of waiting one clock, (d) two lanes for level 3 (it requires at least two slices per picture).

## 4b. Area and Fmax of the coefficient path (probe `tools/probes/tvc_blk`, V-225)
Range decoder + bin layer + block decoder fitted together (Cyclone V 5CEBA4F23C8, 4.0 ns constraint, VM stage blkprobe-2, 10 minutes): **128.3 MHz at slow 85C, 127.4 MHz at slow 0C**; the critical path is still the range decoder's multiplier stage (`rhi_r` -> DSP -> `a_bound`), so the new block and bin logic is not the limit; 429 ALMs (probe wrapper included), 573 registers, 1 DSP, one M10K (the 407 contexts). About +2.2 ns of slack at 100 MHz standalone.

## 4c. The fast engine (`tau_tvc_eng.sv`, V-226)
One module with the context RAM, the range decoder and the block decoder, replacing the request / answer handshake by look-ahead: while a bin is in its compare clock the next bin (context, bypass or not, end of block) is worked out for both values of the bit and the late bit selects one; its context goes to the RAM read address at the end of that clock, so the next probability is ready when the bin commits; the probability a bin writes back is forwarded when the next bin uses the same context. Single bins for the macroblock layer keep a request / answer port (about 8 clocks each). Same checks as the layered version (`make test-rtl-tvc-eng`: all 8 traces, both variants, every level, every context number, range / code, steady and throttled bytes; 8 mutants killed incl. forwarding, select, write-back, warm-up).
* **`FAST = 1` (default): 3.03 to 3.11 clocks per bin in blocks** (v01 3.07, v02 3.11, v04 3.05, v13 3.08, v14 3.03, v15 3.11), against 7.7 for bin + blk: **2.5 times faster, 33 M bins/s at 100 MHz, 22 M bins/s at 66.67 MHz**. Fit alone: **94.8 MHz (slow 85C) / 94.0 MHz (slow 0C)**, 456 ALMs, 1 DSP, 1 M10K; critical paths the compare stage with the late bit's fan-out (10.5 ns) and the RAM output through the forwarding mux into the multiplier (10.6 ns). So it **closes at 66.67 MHz (about +4 ns) but not at 100 MHz.**
* `FAST = 0`: 4 clocks per bin, the registered bit selects the next context and the probability is written before it is read (no select fan-out, no forwarding). Fit alone 98.4 MHz: the RAM output -> multiplier path (10.2 ns) limits it, so it gains nothing over `FAST = 1`; kept as a documented, tested variant. A fabric register between RAM and multiplier did not help either: Quartus folds it into the RAM output register, and forcing it with `preserve` turned the whole memory into 8,325 registers (106 MHz, rejected).
* **What would reach 100 MHz and beyond (not done):** the multiplier stage is the structural limit (7.4 ns in the range decoder alone, 9 to 10 ns in the engine). Both multiplier operands need to be registers that the DSP block can absorb, i.e. an explicitly pipelined multiplier (operand capture, then multiply: 4 clocks per bin at an estimated 125 MHz or more, 25 M bins/s at 100 MHz). That is the next speed step if the parser has to run on the 100 MHz domain.

## 4d. The macroblock layer (`tau_tvc_mb.sv`, V-228)
Parses one macroblock at a time: the header bins through the engine's single-bin port (about 8 clocks each), every coefficient block through its block port (3 clocks per bin). The caller gives the macroblock's column and whether its left / above neighbour is unavailable (picture edge, another slice). Output: the macroblock record (type, lists, QP, chroma and four luma intra modes, coded flags, transform sizes, sub-block flags, the four motion vector differences) and the levels tagged by block / sub-block. Not in it: motion vector prediction (it needs the vectors, not the bins) and dequantisation.
**Verification (`make test-rtl-tvc-mb`):** every vector under `tools/tvc_ref/vectors` (21: P and B pictures, adaptive QP, 4x4 transforms, quarter-pel, odd crops, 1 to 36 slices per picture, Level 1 to 3 syntax), steady and throttled byte supply: **185,996 macroblocks, every header field and every level of every coded block equal to the reference's** (macroblock records and coefficient arrays from `tvc_rc_trace` -> `X.mb.txt`); the testbench can also compare the engine's bin sequence with the reference's per slice (`+bins=`) and prints the first diverging bin: it found a real width bug (the neighbour class sum of two saturated motion vector differences, 16 + 16, wrapped in 5 bits). 8 mutants killed (the 5-bit wrap, a context that ignores a neighbour in skip / coded flag / transform size, wrong most probable mode, wrong remainder mapping, the QP delta context, the upper QP clip). Two vectors were added for the last one (v20 reaches QP 51 on 204 macroblocks, v21 QP 0 on 174): none of the first 19 ever reached the clip.
**Speed:** 303 clocks per macroblock averaged over the 21 vectors at the engine's 3 clocks per bin. The Level 3 budget on `clk_sys` is 66.67 M / 67,500 = 987 clocks per macroblock: the typical streams are about 3 times inside it (v01 246, v02 185, v13 125, v17 117), **two of the vectors are over: v14 (all-intra, QP 16) 1,881 and v21 (QP 0, about 100 bytes per macroblock, still inside the level's 384 KB per picture) 3,036.** So one parser on `clk_sys` keeps up with typical Level 3 content but not with legal high-bitrate pictures: this is the case the upgrade path is for (two parsers on different slices, or the pipelined-multiplier engine on a faster clock).

## 4e. Vector prediction (`tau_tvc_mvp.sv`, V-229)
A sequence per macroblock: `mb_start` (column and which neighbours are missing) -> `pv_valid` with the prediction of both lists -> `commit` (type, lists, differences from the macroblock layer) -> `o_valid` with the final vectors. It keeps the vectors of the left macroblock, of the row above (a line buffer by column) and the above-left vector the next column needs. Packing as in the macroblock layer: [list][component] 16 bits, [0][0] in 15:0 up to [1][1] in 63:48.
**Verification (`make test-rtl-tvc-mvp`):** the reference's macroblock records of all 21 vectors (`M` lines now end with the final `mv`), no engine needed: **185,996 macroblocks (48,026 intra, 53,318 inter, 84,652 skip; 86,468 with a non-zero vector): the final vectors equal the reference's exactly**, and the prediction is checked through the reference's own relation (inter: mv = pred + mvd for each used list, skip: mv = pred). 6 mutants killed (a median that ignores the third vector, no above-left fallback, no left fallback when the above row is missing, a wrong above-left register, a left register that skips skip macroblocks, a subtracted difference). One "mutant" turned out to be a correct median written differently (equivalent) and was replaced.

## 4f. Area and Fmax of the whole parser (engine + macroblock layer + vector prediction, V-229)
Fitted together (probe `tools/probes/tvc_parse`, Cyclone V 5CEBA4F23C8, 10 ns constraint): **1,438 ALMs (8 % of the device), 1,742 registers, 3 M10K (the 407 contexts, the neighbour state, the vectors), 1 DSP; 96.1 MHz (slow 85C) / 93.7 MHz (slow 0C): about +4.6 ns of slack at the 66.67 MHz of `clk_sys`.** The first build was 5,366 ALMs: the vector prediction read its line buffer twice in one clock (two read ports), Quartus could not infer a RAM and built 4,096 flip-flops; reading the entries one per clock through a single registered port (both units are slow enough) gave the 1,438.

## 5. Decision: the parser runs on clk_sys, 66.67 MHz (V-228)
Decided by Claude (the owner asked for the architecture to be decided, 2026-10-29). **The parser uses the fast engine as it is (`FAST = 1`, 3 clocks per bin) on `clk_sys`.** Reasons: (1) it closes there today (about +4 ns standalone) and gives about 22 M bins/s, almost what a 4-clock engine would give at 100 MHz (25 M bins/s), which would first need the pipelined multiplier; (2) the slice bytes arrive through the CPU / bridge in the `clk_sys` domain, so the parser sits next to its input; its output (levels and syntax elements, far below 30 M words/s) crosses once to the SDRAM-clock decoder through a dual-clock FIFO; (3) 22 M bins/s is about 3.5 times the level 3 average (about 6 M bins/s, estimate). **Risk:** the worst legal picture (384 KB, about 9 bins per byte in the test vectors, so about 3.5 M bins) takes about 160 ms on one parser, 5 picture periods; quantified and closed in section 6 (one parser is enough with a decode-ahead of 8 pictures at level 3). **Upgrade path if peak pictures need more:** two parsers on different slices (level 3 requires at least 2 slices), or the explicitly pipelined multiplier (4 clocks per bin, estimated 125 MHz or more) for a 100 MHz domain; the layered units and `PIPE` / `FAST` parameters stay for that.

## 6. The throughput gap, quantified and closed (V-229)
V-228 compared the parser with the per-macroblock budget of the level 3 maximum macroblock rate (987 clocks at 66.67 MHz) and found all-intra / QP 0 pictures over it. That budget is the wrong yardstick: the level caps the **bytes**, too (TVC_BITSTREAM_V0.md section 8: at most 384 KB per level 3 picture and 600 KB in any second), so a picture that costs 1,900 to 3,000 clocks per macroblock can only occur in bursts, and the question is how far behind the display the parser can fall and what that costs in buffering. Measured model (`tools/tvc_ref/parse_budget.py`, from the 21 vectors): **clocks = 3.17 x bins + 35 x macroblocks**, about 9.4 bins per byte (8.0 to 12.4), i.e. about 30 clocks per byte: **one parser on `clk_sys` parses about 2.2 MB/s** of bitstream, against at most 600 KB/s on average at level 3: **30 % busy over any full byte window, whatever the content.**
**Worst burst:** the legal stream that packs the most bytes into the first pictures (a 384 KB picture, a 216 KB one, then tiny pictures): the parser falls **204 ms behind** the display at 30 fps (187 ms at 24 fps) after the second picture and recovers within the next 7 pictures. **So one parser is enough if the player decodes ahead by 8 pictures at level 3, 30 fps (6 at 24 fps; level 2: 5 and 4; level 1: 2)**, i.e. starts the display about 270 ms after the first picture (250 ms at 24 fps). Sensitivity: sparse content with 12.4 bins per byte (the low-bitrate end of the vectors) needs 10 pictures, 14 bins per byte 12.
**What it costs:** the decoded pictures wait in SDRAM: 8 ahead + 2 anchors + the displayed one + the one being decoded = 12 slots of 864 KB (800 x 720 4:2:0) = 10.4 MB of the 64 MB. **This breaks one earlier assumption**: the memory map of the controller exchange had picture slots 8 MB apart (2^22 words, bits 24:22 select the slot, 8 slots): 12 slots do not fit; the slots must be packed (about 1 MB apart or less) and the bank hash re-chosen with the replay (contract `BANK_HASH`). The **bitstream must be prefetched too**: the SD card delivers 1.4 MB/s in large reads (measured, V-218), slower than the parser's 2.2 MB/s, so a 600 KB burst takes the card 430 ms against 270 ms of parsing: a bitstream FIFO of at least 1 MB (PSRAM) filled at least half a second ahead.
**Options if the 270 ms start-up or the memory are not acceptable (none needed to be correct):** two parsers on different slices (level 3 requires 2 slices; 4 pictures ahead, 133 ms), 2.2 clocks per bin (the dual-read engine, 5 pictures), or the 100 MHz pipelined-multiplier engine (5 pictures); the layered units and the `PIPE` / `FAST` parameters stay for that. The downstream transform / motion compensation must also absorb the burst: motion compensation costs 1.5 M SDRAM cycles per heavy picture (15 ms at 100 MHz, V-219), the transform is not designed yet (open).

## 7. Dequantisation and inverse transform (`tau_tvc_itx.sv`, V-230)
The first glue between the parser's level stream and the pixels (TVC_BITSTREAM_V0.md section 6.1). Per block: `start` (QP, 8x8 or 4x4 sub-block, which quarter), the parser's `(scan index, level)` pairs in any order (dequantised on the way in: `sign * min(32767, (|l| * QS[qp] + 8) >> 4)`, placed by the zig-zag), `go`, then the residual one sample per clock in raster order (`out_y` / `out_x` include the sub-block offset), `done`. **An 8-point dot product of 8 multipliers does both stages** (stage 1 `e = clip((sum T[u][y] * C[u][v] + 64) >> 7)`, stage 2 `r = (sum e * T + 128) >> 8`; 4x4: T4 and `+64 >> 7` twice) one result per clock; all-zero columns of C are skipped. **Speed: 113 to 121 clocks per block including loading the levels** (about 120 for a dense 8x8, the testbench feeds one level per 2 clocks): a heavy level 3 picture of 13,500 coded blocks takes about 1.6 M clocks = 24 ms at 66.67 MHz, well below the parser's 170 ms burst, so **the transform is not the bottleneck** (the burst analysis of section 6 stands).
**Verification (`make test-rtl-tvc-itx`):** vectors made with the reference's own `dequant`, `inv_transform` and `inv_transform4` (`tools/tvc_ref/tvc_itx_vec`): **30,000 random blocks (every density, every QP with extra weight on 0..3 and 48..51, levels up to the int16 extremes so that the dequantiser's clip and the stage 1 clip are hit, half of them fed in random order) and 96,707 real blocks (79,616 8x8, 17,091 4x4 sub-blocks) of 7 vectors**, with and without random gaps between the levels: every one of the 64 / 16 samples, its order and its coordinates equal the reference's. 4 mutants killed (QS truncated to 11 bits, rounding 7 instead of 8, the sign ignored, the 8x8 stage 2 rounding 64 instead of 128).
**Area and speed:** probe `tools/probes/tvc_itx`: **123.0 / 120.6 MHz, 1,296 ALMs (7 %), 2,291 registers, 8 DSP blocks (12 %), no RAM**: closes at 100 MHz (+1.7 ns) and at 66.67 MHz (+6.7 ns). Not here: the prediction (intra from the current picture, inter from the reference pictures), the add and clip to 0..255 (a pred + residual stage, like `tau_mp4v_recon`), the deblocking (TVC section 7), the chroma 4:2:0 handling of vectors: the next pieces of the decoder.


## 8. Intra prediction and add + clip (`tau_tvc_recon.sv`, V-232)
One unit with an 8x8 prediction buffer (64 bytes), the intra predictor that fills it (TVC 6.2: DC, vertical, horizontal, planar, the availability substitutions in the stated order; the caller gives mode, which neighbours exist and the 8 samples above / 8 to the left) and the add-and-clip pass (`pred + residual`, clipped to 0..255, residual from `tau_tvc_itx` in raster order with gaps allowed, or `nores` for uncoded blocks / skipped macroblocks). An external predictor (the inter unit) can fill the buffer through `pw_*`. Speed: 64 + 4 clocks to predict an intra block, 64 + 3 for the add pass.
**Verification (`make test-rtl-tvc-recon`):** the reference now has a guarded hook (`TVC_PRED_HOOK` in tvc.h; no effect on the decoder or encoder) and `tvc_pred_trace` writes the neighbours, prediction, residual and the pre-deblocking output of every reconstructed block (10 vectors, every 8th block after the first 4000, plus 30,000 random blocks from `tvc_pred_random` with flat, extreme, ramp and noise content, every availability combination, residuals up to +-500,000). Intra: the prediction alone (a pass with `nores`) equals the reference's, then with the residual the output equals the reference's output; inter / skip blocks: the reference's prediction written through `pw_*` plus the residual equals its output; with and without gaps. 12 mutants killed (the random trace was needed to kill the upper clip: real content rarely saturates). Findings: the RAM read address must be the combinational request address (a registered address made every flat block pass and the first ramp fail).
**Fit probe (`tools/probes/tvc_recon`):** first build -2.9 ns at 10 ns (planar: four products and the sum in one stage); with the products registered **+2.34 ns at 10 ns, 292 ALMs, 683 registers, 4 DSP, 1 M10K** (about 130 MHz).

## 9. Inter prediction (`tau_tvc_inter.sv`, V-232)
One block (16x16 luma or 8x8 chroma) from one reference plane; the vector is always the luma vector. **One separable pipeline serves every case of TVC 6.3**: `clip((sum_j FV[j] th(j) + 2048) >> 12)`, `th(j) = sum_k FH[k] R(X+k-1, Y+j-1)`, filters summing to 64, the identity filter (0,64,0,0) collapsing the one-dimensional cases ((64 * 64 * a + 2048) >> 12 = a, (64 S + 2048) >> 12 = (S + 32) >> 6): mode 0 luma half sample (filters (0,32,32,0)), mode 1 luma quarter sample (the four 4-tap filters), mode 2 chroma 1/8 weights (filters (0, 8 (8-f), 8 f, 0): the reference's `(... + 32) >> 6` is the same arithmetic), mode 3 chroma half sample (the vector halved toward zero, then as mode 0). The (bw+3)^2 window is requested in raster order, one request per clock, coordinates **already clamped** (the edge replication), answers in order after any latency; the horizontal filter works on a 4-sample register as the samples arrive, the vertical filter on three delayed rows (a 48-entry shift chain), so no window RAM is needed. Output in raster order, then `done`. Not here: bi-prediction averaging of the two lists, the assembly of a macroblock (16x16 + 2 x 8x8) and the memory side (the row-burst fetch layer / TREQ 2D reads that turn the sample requests into bursts; the window is at most 19 x 19 samples, within the 10 x 19 words of the controller exchange).
**Speed (simulation, latency 1):** about 225 clocks per block; a macroblock (one luma + two chroma blocks) is about 225 + 2 x 90 = 400 clocks per list, so a bi-predicted macroblock is about 800 clocks, inside the clk_sys budget of 987 clocks per level 3 macroblock only when the memory keeps up (the sample-at-a-time request port is the limit; the row-burst layer is the next piece).
**Verification (`make test-rtl-tvc-inter`):** `tvc_inter_random` makes planes of 8x8 up to 64x64 (flat, extreme, ramp, checker, noise) and random blocks with the reference's `inter_pred`, `inter_pred_q`, `inter_pred_c8`, `chroma_mv` (vectors up to +-3000, so most blocks reach or leave the edge): 9,600 blocks per trace (all four modes), latency 1, 3, 6, with random ready gaps; every sample equals the reference's, raster order and coordinates are checked, no request may leave the plane. 12 mutants killed. Finding: a signed shift on an expression that contains a concatenation is a logical shift (the chroma vector halving); caught by the very first mode-3 block.
**Fit probe (`tools/probes/tvc_inter`):** the first build was -2.9 ns at 10 ns; the cure was the same each time: **register the products and sum them in the next stage**, for the vertical stage (tap mux in front of the multipliers, then the products) and for the horizontal one. Final: **+2.10 ns (slow 85C) / +1.65 ns (slow 0C) at 10 ns, 694 ALMs, 1,262 registers, 8 DSP, no RAM** (about 120 MHz); closes on clk_sys and clk_sdram.

## 10. Deblocking filter and boundary strength (`tau_tvc_dbk_f.sv`, V-232)
`tau_tvc_dbk_f`: the filter of one line across an edge (alpha, beta, tc from QS[qp], the three tests, the clipped delta, p0 and q0 only), combinational. `tau_tvc_dbk_bs`: the strength (intra 2; coded block 1; different macroblocks with different motion 1; else 0) from the two blocks' flags, lists, vectors and the qpel flag; chroma passes "coded != 0" as the block bits. **Verification (`make test-rtl-tvc-dbk`):** 120,000 filter lines (near the thresholds so all three tests flip, extreme values, every QP, both strengths) and 120,000 strength cases (luma pairs inside and across macroblocks, chroma pairs, vectors around the threshold) against `filt_line`, `bs_luma`, `bs_chroma`; 9 mutants killed (two first-draft strength mutants were equivalent and were replaced). **Fit probe (`tools/probes/tvc_dbk`):** 328 ALMs, 848 registers, no DSP, **+0.82 ns at 10 ns with the combinational units between registers** (about 108 MHz). Not here: the picture-level scan (edge order: all vertical edges then all horizontal ones over the whole picture, using the vertically filtered samples; the qp mean of the two macroblocks; the per-macroblock metadata store) and its memory traffic.

## 11. What is left of the decoder
Bi-prediction average and macroblock assembly around `tau_tvc_inter`; the memory side of the inter unit (row-burst / TREQ reads) and of the reconstruction (picture write-back, intra neighbour fetch: the row above and the column to the left of each block); the deblocking scan and its metadata; the integration top (parser -> vector prediction -> transform / prediction -> reconstruction -> deblocking) and the clk_sys -> clk_sdram FIFO; memory map with packed picture slots + the PSRAM bitstream FIFO; then TAC IMDCT RTL.

## 12. Macroblock reconstruction (`tau_tvc_mbrec.sv`, V-233)
Sequences `tau_tvc_inter` and `tau_tvc_recon` over one macroblock, bit-exact with `tvc_recon_mb()` (pre-deblocking). `tau_tvc_recon` grew to eight 8x8 prediction slots (luma 0..3, Cb 4, Cr 5) and an averaging write (`pw_avg`: (old + new + 1) >> 1 through the single shared read port), so no copy between a macroblock buffer and the reconstruction is needed. **Inter / skip:** each used list predicts the luma block and the two chroma blocks straight into the slots, the second list of a B macroblock (`uses = 3`) averaging in; then the six blocks are added to their residuals and written to the current picture. **Intra:** per block (luma 0..3, Cb, Cr) the 8 samples above and 8 to the left are read from the current picture (only those that exist: slice start, picture edge), predicted, added, written back before the next block. Memory is abstract: reference reads are single-sample requests (list, plane, clamped x, y), current-picture reads one outstanding, writes accepted at once, residual requested with `rb_req` per coded block (the transform's 8x8 raster; for 4x4 blocks the integration must assemble the 8x8).
**Verification (`make test-rtl-tvc-mbrec`):** `tvc_mb_trace` (guarded `TVC_MB_HOOK`) writes, per macroblock, the record, the six residuals and the 384 reconstructed samples, and per picture the two reference pictures as the reference decoder predicts from them. Seven small vectors (odd crops, B pictures with all list combinations, quarter-sample, 4x4 transforms, slices, QP 0 and 51): **every macroblock's 384 samples equal the reference's**, with the current picture starting as noise (an unwritten neighbour read would fail) and with random fetch stalls and latency 2 / 5. 11 mutants killed (second list overwrites, list 1 vector from list 0, chroma in luma mode, wrong left neighbour, slice start ignored, wrong chroma intra mode, wrong chroma plane, swapped chroma coded flags, every list averages, averaging rounds down, averaging replaced by overwrite).
**Speed (simulation, fetch latency 2, one sample per request): intra 1,111 clocks per macroblock (max 1,140), inter 1,157 average (max 1,721), a bi-predicted skip macroblock 1,556. The level 3 budget on clk_sys is 987 clocks per macroblock (67,500 macroblocks per second at 66.67 MHz), so this version is too slow for the worst legal rate**; typical content is far below the maximum rate (a 800x334 picture at 24 fps is 837 macroblocks x 24 = 20 k per second, 3,300 clocks available each). Where the clocks go, for a one-list inter macroblock: prediction about 405 (225 luma + 2 x 90, sample-at-a-time window requests), draining 12, six add passes about 408 (64 + 3 each, one sample per clock). Planned cures, none built: overlap the add passes of macroblock n with the prediction of n+1 (a second slot bank), add two samples per clock, prediction windows from row bursts (the 19 x 19 window is 361 requests today), neighbour samples for intra from a line buffer instead of 16 reads per block (about 100 clocks of the intra macroblock).
**Fit probe (`tools/probes/tvc_mbrec`, unit + inter + recon):** **+1.49 ns (slow 85C) / +1.05 ns (slow 0C) at 10 ns, 1,135 ALMs (6 %), 2,268 registers, 12 DSP, 1 M10K.**

## 13. Macroblock unit, second version: overlap and parallel units (V-234)
The macroblock unit of section 12 was too slow (intra 1,111, inter 1,157, bi-predicted skip 1,556 clocks per macroblock). Changes, all still bit-exact against the reference (`make test-rtl-tvc-mbrec`, now with overlapped starts: a `ready` / `start` handshake and a queue of up to four macroblocks in flight, completed in order):
* **Two inter units in parallel** (luma; chroma Cb then Cr), each with its own reference-fetch port (`rfl_*`, `rfc_*`) and its own write port into the prediction slots: the prediction of a list takes about 370 clocks instead of 611.
* **Prediction and pass overlap:** `tau_tvc_recon` has two banks of prediction slots (a luma memory of four blocks and a chroma memory of two per bank, each with its own read port); a prediction engine fills one bank for macroblock n+1 while a pass engine adds the residuals of macroblock n from the other and writes it to the current picture. An intra macroblock starts only when everything is idle (its neighbours are the previous macroblocks' results); an inter one may start while a pass runs.
* **Intra:** the 16 neighbour samples are requested one per clock (answers in order) instead of one at a time, and the add pass starts 9 clocks after the prediction starts, trailing the predictor's writes.
**Measured (no stalls, 7 vectors; clocks between completions, average / maximum):** intra 570 / 586 (was 1,111), inter 430-515 / 757-805 (was 1,157 / 1,721), skip 416-704 (was 1,556); the 1,173 maximum is the first macroblock of a picture: the testbench drains the queue at every picture header, so that macroblock has nothing to overlap with (752 clocks of bi-prediction + 415 of pass). Traced (V-234): in a run of bi-predicted macroblocks the unit is **prediction-bound at about 755 clocks per macroblock** (list 0 and list 1 predicted one after the other, about 376 each: the 19 x 19 window is 361 single-sample requests), the pass (415) is hidden. The level 3 budget is 987 clocks per macroblock at the maximum rate on clk_sys (1,481 on a 100 MHz clock): **steady state is inside it everywhere (worst 755), with a 1.3x margin on clk_sys; the 1,173 is a pipeline fill that only matters if a picture's first macroblock can not start before the previous picture is finished** (in the real decoder the next picture's first macroblock waits for the previous picture's deblocking only if it is a reference of it). Further cures if needed: window trimming for integer vectors (256 instead of 361 samples), a second pair of units for list 1, two samples per clock in the pass.
**Verification:** 14 mutants killed (the 9 of section 12, plus add pass without the margin, one bank for both macroblocks, wrong coded flags handed over, and the two averaging mutants of `tau_tvc_recon`); recon's own test and 12 mutants unchanged.
**Fit (probe `tools/probes/tvc_mbrec`):** 1,409 ALMs (8 %), 2,897 registers, 4 M10K, 20 DSP. **Slack -0.29 ns (slow 85C) / -0.68 ns (slow 0C) at 10 ns on a path inside the memory blocks** (write enable to data register, a clock skew of -2.2 ns; `no_rw_check` made no difference): it **closes at 66.67 MHz (about +4 ns) but not at 100 MHz.** Run the unit on clk_sys, next to the parser, or find the cause before moving it. Two findings on the way: (1) a 2-D array of memories (`mem[bank][addr]`) and a write chain of several if / else-if branches with different addresses were built as 6,000 flip-flops (5,700 ALMs) with no message; one memory per bank and class, and a single write port (enable, address and data chosen first, then `if (we) mem[a] <= d`), gave 4 M10K; (2) a synthesis-only run (`quartus_map`, about a minute) shows this immediately: use it before a full fit when a memory is involved.

## 14. Macroblock unit, third version: 100 MHz and both lists in parallel (V-235)
* **100 MHz:** the miss of section 13 (a path inside the memory blocks, write enable to data register) was cured by **registering the write controls (enable, address, data) in front of each prediction memory** (probe variants on the old design: registered writes +1.02 / +0.64 ns at 10 ns; MLAB instead of M10K: no change, the tool kept M10K). The add pass trails the predictor by far more than the extra clock.
* **Bi-predicted macroblocks:** list 0 and list 1 are predicted at the same time by their own luma and chroma units (four `tau_tvc_inter`) into their own sets of prediction memories (per bank: luma and chroma memory for each list, eight memories in all); `tau_tvc_recon` no longer has the read-modify-write average: its add pass reads both sets and averages (`r_sel` 1 list 0, 2 list 1, 3 average, one more pipeline stage). The prediction of a bi macroblock now takes about 390 clocks (was 750) and the unit is bound by the pass (about 415 clocks).
**Measured (no stalls, clocks between completions, average / maximum; section 13 in brackets):** intra 575 / 590 (570), inter 422-460 / 426-809 (430-515), skip incl. bi-predicted 422-448 / 422-805 (416-704 / 1,173). The 805 maxima are the pipeline fill at the start of a picture (prediction 390 + pass 415, the testbench drains the queue at each picture). **Every steady-state case is now about 420-580 clocks, under half of the 987-clock level 3 budget on clk_sys (1,481 at 100 MHz).**
**Verification:** 15 macroblock-unit mutants killed (the 14 of section 13 with the old averaging mutants replaced by: bi macroblock uses list 0 only, list-1-only macroblock reads set 0, average rounds down, average replaced by set 0, `r_sel` 2 reads set 0); recon's own test and 12 mutants unchanged.
**Fit (probe `tools/probes/tvc_mbrec`, unit + four inter + recon):** **+1.06 ns (slow 85C) / +0.75 ns (slow 0C) at 10 ns: closes at 100 MHz.** 2,329 ALMs (13 %), 4,877 registers, 8 M10K, **36 DSP (55 % of the device: the four inter units use 8 each, the planar products 4; the whole decoder still needs the transform's 8 and the parser's 1, but this is the largest DSP consumer)**. The memory side will have to serve four reference ports (two lists x luma / chroma) instead of two.

## 15. Deblocking picture scan (`tau_tvc_dbk.sv`, V-236)
Bit-exact with `tvc_deblock()`: luma vertical edges, luma horizontal edges (on the vertically filtered samples), then Cb and Cr the same way. The filter reads two samples on each side of an edge and changes only p0 and q0, and edges are 8 samples apart, so the edges of one pass do not interact; the unit walks **8-line segments** (one edge between two 8x8 blocks): it reads the two macroblocks' records (80 bits: type, qp, coded bits, lists, vectors), takes the strength from `tau_tvc_dbk_bs` and the mean qp, **skips the segment when the strength is 0**, otherwise reads the 4 samples of each of the 8 lines (one request per clock, answers in order), filters with `tau_tvc_dbk_f` and writes back **only the samples that changed**. Chroma uses "coded != 0" of the whole macroblock for the strength and the macroblock pair itself; luma uses the coded bit of the 8x8 block and the same-macroblock rule. A plane one block wide or high has an empty pass. Memory is abstract (single-sample reads and writes, record read by macroblock index); the metadata store that the parser / macroblock unit would fill is not built.
**Verification (`make test-rtl-tvc-dbks`):** `tvc_dbk_trace` (guarded `TVC_DBK_HOOK`) writes, per picture, the macroblock records and the picture before and after the reference's deblocking: 8 vectors (odd crops, B pictures, quarter-sample, 4x4, slices, QP 0 and 51, and 800x336 pictures), memory latency 1 and 4: **every sample of every picture (Y, Cb, Cr) equals the reference's.** 12 mutants killed (horizontal first, chroma strength by the luma rule, qp mean without +1, block P from Q's macroblock, strength 0 not skipped, Cr skipped, chroma strength raised, only p0 / only q0 written, chroma qp from P only, luma block bit swapped, last vertical edge skipped; one first-draft mutant, same-macroblock flag, was equivalent and was replaced). The first run on an 800 x 336 picture failed only because the testbench memory was too small.
**Speed (simulation, memory latency 2, one sample per request):** 368,800 clocks for an 800 x 336 picture (3.7 ms at 100 MHz, 5.5 ms at 66.67 MHz); level 3 (800 x 720) would be about 790 k clocks, 7.9 ms at 100 MHz = 24 % of a 33 ms picture period at 30 fps (36 % on clk_sys). Segments with strength 0 cost only the two record reads. Real SDRAM will be slower with single-sample accesses: the row-burst version (a vertical-edge segment is 8 rows of 4 contiguous samples, a horizontal-edge segment 4 rows of 8) belongs to the memory side.
**Fit (probe `tools/probes/tvc_dbks`):** **+1.63 ns (slow 85C) / +1.35 ns (slow 0C) at 10 ns: closes at 100 MHz.** 499 ALMs, 772 registers, 2 DSP (the macroblock index multiplier), no RAM.

## 16. Memory side against the controller contract (V-237)
Built against Tau Alpha's **client port protocol** (`tau-alpha/docs/features/SDRAM_CONTROLLER_CONTRACT.md` section 4, **v0.8 draft** as found in that repo; registered `req_ready`, 16-bit word addresses, write data pulled with a fixed lead of 2, read data pushed with `r_last`, 2D reads w <= 63 words, h <= 63 rows, w x h <= 512, stride <= 2,047) and a behavioural model of one port (`sim/sdram_port_model.v`: request queue, latency, optional bubbles, rejection of illegal requests, in-order reads, write pull with the 2-cycle lead and `done`). The model knows nothing of banks, refresh or other ports: it is a stand-in until the real controller (or its chip-model replay) is used.
* **`tau_tvc_wfetch`** (reference window fetch): when the inter unit starts, it learns the window (the inter unit now exports `win_*`), reads the part inside the plane as **one 2D request** (at most 10 words x 19 rows = 190 words, 16-bit words, two samples each, even sample in bits 7:0), keeps it in a local 512-word buffer and answers the inter unit's sample requests from it, one per clock; edge replication needs no memory access (a clamped coordinate lies in the rectangle that was read). Verified through the inter traces: **2,400 blocks per run, all four modes, edges and far-outside vectors, equal to the reference; controller latency 3 / 6 / 14, with bubbles; no 2D request outside the plane's words and none rejected**; 6 mutants killed. Cost per block: **about 291 clocks instead of 225** (the controller latency of 6 plus the burst before the first sample), so a macroblock's prediction time grows by about 25 % unless the next window is prefetched during the previous one (not done: the buffer is single). Fit: **195 ALMs, 1 M10K, 1 DSP, +2.9 ns at 10 ns.**
* **`tau_tvc_rdarb`** (4 clients onto one read port): the macroblock unit has four fetchers (two lists x luma / chroma) but the controller gives the decoder ONE read port; the arbiter takes one request at a time (round robin), forwards it with registered handshakes and routes the in-order read data to the client at the head of a queue of issued requests. Each client has one request outstanding, so the contract's read credit rule holds by construction. Verified with four random clients (1,200 requests, 50 k words, every word and `r_last` per client) at four controller configurations including one that refuses requests; 5 mutants killed (an equivalent tag mutant was replaced).
* **`tau_tvc_wr`** (picture write-back): the macroblock unit's samples (plane, x, y, byte) are collected in a macroblock-row buffer of **G = 4 macroblocks** (two buffers: one fills while the other is flushed) and written as **32 requests per group** (16 luma rows of up to 32 words, 8 + 8 chroma rows of up to 16), up to three outstanding, data read from the buffer when the controller pulls it (`w_next` / `w_idx` -> RAM read -> `w_data` exactly two cycles later); partial groups at the end of a row are written with their real length. Handshake with the macroblock unit: `mb_done` / `done_x` / `done_y` in, `wr_ok` out (the unit holds the next pass while the buffer it would fill is still being flushed; a clock of delay after `done` lets the buffers switch), `idle` for the picture barrier. Verified through the macroblock traces: **the picture in the controller's memory equals the reference's picture, every sample of every picture of 7 vectors, normal and slow write controllers**; 8 mutants killed (byte lanes, Cr offset, partial-group length, group boundary, data a clock early, `wr_ok`, chroma row, group origin). Fit: **155 ALMs, 8 M10K, +3.4 ns at 10 ns.** Two Quartus findings: partial-word writes into a 16-bit array became 25,000 flip-flops (use one 8-bit RAM per byte lane in the plain template), and the register summary of `quartus_map` is "N/A until Partition Merge" in the report that must not be confused with a stale file.
* **`tau_tvc_mdstore`**: 80-bit macroblock records (2,304 deep, about 18 M10K, a second copy for decode-ahead), used by the deblocking scan test now (still passes on all 8 vectors).
**Not done, and the main open problems:**
1. **Intra neighbours** are still read from an abstract current-picture memory. The real data path can not be the SDRAM: the neighbours (the macroblock to the left, the row above) may still sit in the write buffer. They need a local store (a 1-sample-high line buffer for the row above, the previous macroblock's right column), which also removes the 16 reads per block.
2. **`wfetch` and `rdarb` are not yet wired into `tau_tvc_mbrec`** (the macroblock unit still has four abstract sample ports); the combined throughput has not been measured. Expect the prediction to be bound by the controller's 2D reads (about 4 x 190 words per bi-predicted macroblock) and a prefetch of the next window is probably needed.
3. **Deblocking and the next picture's references** read and write the picture in SDRAM one sample at a time: the row-burst version (and the ordering against the write-back: `idle`) is open.
4. Picture slots, the bank hash and the PSRAM bitstream FIFO (needs the real controller and Tau Alpha's replay).

## 17. Intra neighbour store (`tau_tvc_nbstore.sv`, V-238)
Closes open problem 1 of section 16: the intra neighbours can not come from the SDRAM (the macroblock to the left or the row above may still sit in the write-back buffer), so the macroblock unit now has a local store that listens to **every** reconstructed sample it writes (inter and skip macroblocks too: P pictures predict intra blocks from them). **Above:** per plane and per column the last sample written in that column; a block's row above is the bottom row of the block above it and a column is written top to bottom, so when a block is predicted the last sample in its columns IS the row above (blocks 2 and 3 see blocks 0 and 1; block 0 sees the previous macroblock row); eight byte-lane memories (lane = x mod 8, 256 words: luma 0..127, Cb 128..191, Cr 192..255) give the eight samples in one read. **Left:** per plane and per row of the macroblock the last sample written in a column with x mod 8 = 7, which is the left neighbour of the next block of the same rows. Availability (slice start, picture edge) stays with the macroblock unit: stale data is never used when a side is unavailable. The unit's `cr_*` read port is gone and the neighbour fetch (16 requests per block) became a two-clock wait.
**Verification:** the macroblock test (7 vectors, with SDRAM write-back) passes with the store, **4 store mutants plus the 23 earlier ones killed** (left column at x mod 8 = 6, Cb and Cr sharing their slots, chroma left rows offset like luma, above lanes off by one; and the left rows of the lower luma blocks). The first run failed on a real bug (the chroma slot address lost its top bit and aliased the luma slots); caught by the second macroblock row of the first vector. **Fit (probe `tools/probes/tvc_mbrec`, whole macroblock unit incl. both lists, store and recon): +1.15 ns (slow 0C) / +1.38 ns (slow 85C) at 10 ns, 2,374 ALMs (13 %), 4,917 registers, 17 M10K, 36 DSP.** Speed: intra about 500-570 clocks per macroblock (the pipelined fetch of V-234 was already cheap; the gain is correctness).

## 18. Window fetchers and the read arbiter inside the macroblock unit (V-243)
`tau_tvc_mbrec` no longer has abstract sample ports: each of the four inter units (luma and chroma of each list) has a `tau_tvc_wfetch` on its sample port, and `tau_tvc_rdarb` merges the four 2D requests onto ONE read port of the controller (`rd_*`, Tau Alpha's section 4 protocol). New inputs: `ref_base` (word address of luma (0,0) of the picture of list 0 and list 1; both lists may name the same picture), `cb_off`, `cr_off`, `y_stride`, `c_stride`. Tested against `sdram_port_model` (`RLAT` 14 clocks to the first word, one request at a time, like `sched_min`): the reference pictures of the macroblock traces are packed two samples per word into the controller memory; **every macroblock's 384 samples and the written picture still equal the reference's on the 7 vectors**, 27 mutants killed (BUG 7 now means Cr read from the Cb plane).
**Throughput with the real fetch path (no stalls, clocks between completions, average / maximum):** intra 494-571 (unchanged), **single-list inter 641-807, bi-predicted skip 648-890, maxima 937-2174 (picture start and write-back stalls of the narrow test pictures)**, against 420-580 with abstract memory (V-235). The level 3 budget is 987 clocks per macroblock on clk_sys (1,481 at 100 MHz): **steady state fits, with a margin of only about 10-30 % on clk_sys for bi-predicted macroblocks.** Where the time goes: the controller read port is the bottleneck. A bi-predicted macroblock reads up to 2 x (190 luma + 2 x 55 chroma) = 600 words in six requests, each with about 14 clocks of latency in this model (22 clocks per 8-word read on the real controller, V-242), served one at a time by the arbiter, about 700-800 clocks; the four inter units finish their 361 / 121 samples in parallel in about 375, so they wait for data. 600 words per macroblock at 2,250 macroblocks and 30 fps is 40 M words/s = 81 MB/s of the controller's 190 MB/s fill rate: the reference reads alone take 40 % of the memory.
**Cures not built:** prefetch of the next window during the current one (the fetch buffer is single), trimming the window for integer vectors (a 16 x 16 block with no fractional part needs 8 words x 16 rows = 128 instead of 190), reading luma and chroma of a list with fewer requests, and a small reference cache (consecutive macroblocks overlap by up to 15 of 19 samples horizontally). **Fit (probe `tools/probes/tvc_mbrec`, synthesis estimate 3,646 ALMs, 61 kbit RAM; full result below if it finished).**

## 19. The integrated decoder (`tau_tvc_top.sv`, V-244): whole pictures bit-exact
`tau_tvc_top` connects the parser (`tau_tvc_eng` + `tau_tvc_mb` + `tau_tvc_mvp`), the record store, the residual service, the macroblock unit with its window fetchers, the write-back, the deblocking scan and a three-client memory arbiter to ONE section-4 controller port. Firmware interface: `pic_start` (size, type, flags, QP, the SDRAM slots of the picture and of its two references, the plane layout), per slice `slice_go` (macroblock rows) with the slice's bytes on `in_*`, `slice_done`, then `pic_end` and `pic_done`. Per macroblock, sequentially: parse (levels go to the residual service as they come), vector prediction, record to the store, then the macroblock unit (it asks the residual service for each coded block). New units: `tau_tvc_resid` (level log + `tau_tvc_itx` + residual stream, also 4x4 sub-block assembly; `make test-rtl-tvc-resid`: every coded block of the 7 vectors equal to the reference, 3 mutants), `tau_tvc_dbkmem` (the scan's per-sample accesses as 1-word requests with a byte enable), `tau_tvc_memarb` (reference reads / write-back / deblocking onto one port, one request at a time).
**Result (`make test-rtl-tvc-top`, `tools/tvc_ref/tvc_top_trace`): the picture in the controller's memory after deblocking equals the reference decoder's picture, every sample of Y, Cb and Cr, for every picture of all 7 vectors** (I, P and B pictures, half- and quarter-sample vectors, 4x4 transforms, slices, QP 0 and 51, odd crops, 160x96 up to 320x176), also with a slow controller (30 clocks latency, read bubbles) and gaps in the byte supply; no controller request was rejected. This is the first time the complete decode chain (bitstream bytes to deblocked picture) is verified end to end, in simulation, against a controller model of Tau Alpha's section 4 protocol.
**What it costs now (not yet a design for speed):** 320x176 (220 macroblocks): about 2.0 M clocks per picture, of which **the slices take 0.45 M (about 2,050 clocks per macroblock: parse, reconstruct and write one after the other) and the write flush + deblocking 1.56 M** (single-sample accesses at 14 clocks of latency). A level 3 picture (2,250 macroblocks) would need about 4.6 M clocks for the slices (69 ms at 66.67 MHz) and about 16 M for the deblocking: **both are far outside the 33 ms picture period**. The known cures: overlap parsing of macroblock n+1 with the reconstruction of n (double-buffered levels and records; the macroblock unit and the transform already overlap internally), row-burst deblocking (8 rows of 4 contiguous samples per vertical-edge segment), the residual service one block ahead, and the 2D-request lowering for `sched_min` (it rejects 2D reads).
**Not done:** the output/display path, firmware and container reader, the clock crossing (the parser on clk_sys, the rest on the memory clock), the whole-core fit, any Pocket run.

## 20. Where the clocks go after the overlap (V-253, measured, simulation, behavioural single-port memory with 14 clocks latency)
Instrumented `tau_tvc_top` on v19 (320x176, 220 macroblocks per picture, 1,273 clocks per macroblock in the slices; I/P/B mix, 2.5 coded blocks per macroblock) and v09 (Level-1-like, 1.7 coded blocks). Per macroblock:
* **Parser:** 599 clocks in `T_PARSE` (159 bins: 3.8 clocks per bin including the engine waiting for the macroblock layer, the range decoder idle 280 of the 599); vector prediction + record store: a few clocks. Worst case v21 (QP min, 969 bins per macroblock): 3,039 clocks per macroblock, bin-bound at 3.1 clocks per bin. A Level 3 stream at 10 Mbit/s is about 150 bits per macroblock, so about 600 clocks: the parser is not the limit at typical rates.
* **Macroblock unit:** prediction engine busy 665 (idle 608), **pass engine busy 804**. The pass waits (S_PS_WAIT) 775 per macroblock: write-back back-pressure (`wr_ok` low) **0 clocks**, residual service busy 523 clocks (2.5 coded blocks x about 210: transform 113-121 clocks then 64 streaming, one block at a time and only after the add pass asks for it), the rest is the 384 sample writes (1 per clock, `cw_valid` 384 cycles per macroblock).
* **Memory:** read channel busy 505 of 1,907 clocks per macroblock (445 words, 4 requests), write channel 556 (384 words): the SDRAM port is nowhere near saturated; the limit is the serial structure of the macroblock unit.
**Conclusion / next cure:** the residual is the dominant avoidable wait. The transform of a coded block depends only on its levels, not on the prediction, so the residual service should transform every coded block of a macroblock as soon as the parser has delivered it (during the reconstruction of the previous macroblock) into a per-bank residual store (6 x 64 x 20 bits x 2 banks, 1-2 M10K) and the add pass just streams from the store at one sample per clock. That removes about 2.5 x 120 = 300 clocks from a 800-clock pass; the floor is then the 384 writes. The prediction engine (665) and the parser (600) become the next limits, both below the Level 3 budget of 987 clocks on clk_sys.

## 21. The player core (V-263, V-264): register block, display, video, whole-core wiring
**Units (all simulated bit-exact):** `tau_tvc_regs` (host registers on clk_sys: IDX / DATA / CMD / STATUS, slots 0..11, commands pic_start / slice_go / pic_end / show / clear, a toggle mailbox to the memory clock, a 256-word dual-clock bitstream FIFO flushed at every slice_go), `tau_tvc_top` (the decoder), `tau_tvc_scan` (one picture row from the SDRAM into line buffers, YUV to RGB565), `tau_tvc_linegen` (per video line: fetch the requested row, convert it, write the line RAM), `tau_tvc_video` (400 x 360 active in 500 x 400 at 12 MHz = 60 Hz, the geometry of mp3_fb, the picture placed at (win_x0, win_y0), black elsewhere, requests the next line at the start of each line, counts late lines), `tau_tvc_core` (these without the SDRAM controller: three section-4 ports) and `tau_tvc_mem` (Tau Alpha's PHY + sched_v: port 0 scan-out urgent while a row is fetched, port 1 decoder reads incl. 2D, port 2 decoder writes, port 3 spare).
**Firmware sequence per picture:** `pic_start` (slots 0..7), per slice `slice_go` (slots 8, 9; wait for busy to drop) then push the slice bytes (slot 14: four bytes, slot 15: one to three), wait for the slice_done flag; `pic_end`, wait for pic_done; `show` (slot 10: SDRAM word address of the picture, slot 11: window position). The picture to show is chosen by the firmware (`tnv3_present` in fw/tnv3_core.h). The layout registers (strides, offsets, size) of the last pic_start describe the picture shown.
**Verification:** `make test-rtl-tvc-core`: the testbench plays the firmware on three asynchronous clocks (clk_sys 15 ns, clk_mem 10 ns, clk_vid 83.3 ns), decodes pictures through the register block, shows each and compares one whole video frame (400 x 360 active pixels, RGB888) with an independently written golden YUV-to-RGB (picture centred, black bars): every pixel equal, no late line; 4 video mutants killed (row off by one, bank not alternating, x offset ignored, RGB expansion). The scan unit's own mutants are in `test-rtl-tvc-scan`.
**Whole core:** `core_game.vh` has a `TAU_TVC` branch (before the memory test branch) that instantiates tau_tvc_core and tau_tvc_mem on the SoC's decoder register bus (MP4V_ENABLE = 1) and takes the video from the core instead of mp3_fb; STATUS carries the register block's bits plus late display lines [15:8], SDRAM init done [30] and PHY fault [31]. Build bundle `tools/tau_v_tvc_qsf_append.txt` (the memory test rc1 bundle with sched_v and the TVC files), map-only check `tools/vm_map.py`.
**Limits of this first core:** 400 x 360 window (TVC level 1 up to 400 x 240; level 2 / 3 pictures of 800 wide need a 37.125 MHz pixel clock, a new PLL output and a new video.json), no UI or on-screen text, no audio (TAC decoder not built), no SD reader or firmware loop yet (the CPU has the bus; `fw/tnv3_core.h` is the container reader), the CPU has no window into the SDRAM, `win_*` / `show_base` cross to the video clock through plain flops (one frame may glitch when they change).
